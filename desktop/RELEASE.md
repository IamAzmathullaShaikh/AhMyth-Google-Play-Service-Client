# Release guide — desktop control panel

Short guide for cutting and distributing a release of the desktop C2 control
panel (`desktop/`). Version is read from `desktop/package.json` (currently
**2.1.0**).

## Artifacts

Built with electron-builder (`cd desktop && npm run build:linux` and/or
`npm run build:win`), output in `desktop/dist/`:

| File | Purpose |
|---|---|
| `AhMyth C2 Control Panel-<ver>.AppImage` | Portable Linux app — no install, just run |
| `ahmyth-c2-control-panel_<ver>_amd64.deb` | Debian/Ubuntu package (`amd64`) |
| `AhMyth C2 Control Panel-<ver>.exe` | Portable Windows app — built by CI (see below) |

All three contain the same app: the Node C2 server core + the Electron
dashboard. Launching any of them starts the panel and serves the dashboard on
`http://127.0.0.1:42474/`.

## Where to host

- **Recommended: GitHub Releases.** Tag the version and the CI workflow
  (`.github/workflows/build-linux-release.yml`) builds the Linux artifacts on
  `ubuntu-latest` **and** the Windows `.exe` on `windows-latest` in parallel,
  computes a `checksums.txt` per platform, and one release job attaches
  everything — no local build needed.
- **Manual upload:** build locally (`cd desktop && npm run build:linux`;
  Windows needs a Windows host or wine: `npm run build:win`), then drag
  `desktop/dist/*` into a new GitHub Release.
- **Apt repo:** host the `.deb` plus a `Packages` index on any static file
  server if you want `apt install` distribution.

## Checksums

Every release ships SHA-256 checksum files generated by the CI workflow — one
per platform (`checksums-linux.txt`, `checksums-win.txt`), so the asset names
never collide. Verify a downloaded file with:

```bash
sha256sum -c checksums-linux.txt     # run in the folder containing the files
sha256sum -c checksums-win.txt
```

Reference hashes of the locally built **2.1.0** artifacts (2026-08-05):

```text
4a161dcbed5d9f92a887b91e35d9eeccb69ecbd5896a995928936aab00a02d08  AhMyth C2 Control Panel-2.1.0.AppImage

```

> The canonical hashes are the ones inside each release's `checksums.txt`;
> local rebuilds can differ slightly (timestamps), so always verify against the
> release you downloaded.

## Code signing (Windows)

The release workflow signs the `.exe` **opt-in** — no secrets, no signing
(everything still builds). Two paths are supported; set both and the pfx wins
so the exe is never signed twice.

> **Honest caveat:** a **self-signed** certificate signs the file but does
> **not** remove the SmartScreen warning — Windows still treats the publisher
> as unknown. Only a certificate that chains to a public CA — a commercial
> code-signing cert (OV/EV) or **Azure Trusted Signing** — moves SmartScreen
> off the download, and even then SmartScreen builds reputation gradually over
> releases. Self-signed is still useful for internal distribution.

### Option A — pfx certificate (self-signed or commercial)

electron-builder signs during `npm run build:win` when these repo secrets exist:

| Secret | Value |
|---|---|
| `WIN_CSC_LINK` | base64 of the `.pfx` file (`base64 -w0 cert.pfx`) |
| `WIN_CSC_KEY_PASSWORD` | pfx password (can be empty) |

Create a self-signed cert (Linux):

```bash
openssl req -x509 -newkey rsa:2048 -keyout key.pem -out cert.pem -days 3650 \
  -nodes -subj "/CN=AhMyth C2 Control Panel" \
  -addext "extendedKeyUsage=codeSigning"   # required — signtool needs this EKU
openssl pkcs12 -export -out cert.pfx -inkey key.pem -in cert.pem -passout pass:
```

Or on Windows: `New-SelfSignedCertificate -Type CodeSigningCert -Subject
"CN=AhMyth C2 Control Panel" -CertStoreLocation Cert:\CurrentUser\My`
(export as pfx from the cert manager).

### Option B — Azure Trusted Signing (real CA, removes SmartScreen)

Requires an Azure subscription: create a Trusted Signing account + certificate
profile (Standard signing), register an app with a **federated OIDC
credential** for this GitHub repo, and grant it the *Trusted Signing
Certificate Profile Signer* role. Then set:

| Secret | Value |
|---|---|
| `AZURE_TS_TENANT_ID` | Azure tenant ID |
| `AZURE_TS_CLIENT_ID` | App registration client ID |
| `AZURE_TS_SUBSCRIPTION_ID` | Azure subscription ID |
| `AZURE_TS_ACCOUNT` | Trusted Signing account name |
| `AZURE_TS_PROFILE` | Certificate profile name |
| `AZURE_TS_ENDPOINT` (repo **variable**) | Region endpoint, e.g. `https://eus.codesigning.azure.net` |

The workflow logs in via OIDC (`azure/login@v2`) and signs every `desktop/dist/*.exe`
with `azure/trusted-signing-action@v0` before checksums are generated, so the
release hashes cover the signed binary. Because Azure signing bills per
signature, it only runs on `v*` tag pushes — manual `workflow_dispatch`
rebuilds stay unsigned (the pfx path, which is free, also signs on dispatch).

## Install

**AppImage (any distro, portable):**

```bash
chmod +x "AhMyth C2 Control Panel-2.1.0.AppImage"
./"AhMyth C2 Control Panel-2.1.0.AppImage"
```

- Older distros may need FUSE 2: `sudo apt install libfuse2` (Ubuntu 22.04+).
- Optional desktop-integration: install [AppImageLauncher](https://github.com/TheAssassin/AppImageLauncher),
  then double-click the AppImage.

**deb (Debian / Ubuntu / Mint):**

```bash
sudo apt install ./ahmyth-c2-control-panel_2.1.0_amd64.deb
ahmyth-c2-control-panel          # launch from the menu or terminal

# uninstall
sudo apt remove ahmyth-c2-control-panel
```

**Windows (portable, no install):**

```text
download "AhMyth C2 Control Panel-2.1.0.exe" → double-click to run
```

The portable exe runs in place — no installer, no admin rights needed. It
writes its state under `%APPDATA%\AhMyth C2 Control Panel`, so deleting the
exe fully removes the app.

> Unsigned builds make Windows SmartScreen show an "unknown publisher"
> warning (click *More info → Run anyway*). Configure code signing to remove
> it — see [Code signing](#code-signing-windows).

All builds keep their state in the standard per-user Electron directories
(`~/.config/AhMyth C2 Control Panel` on Linux), so uninstalling leaves your
victim lab and captures intact.

## Cutting a release (CI path)

```bash
# 1. Bump the version (keeps tag and artifact names in sync)
cd desktop && npm version patch    # or minor / major
git add desktop/package.json desktop/package-lock.json && git commit -m "chore: bump version"

# 2. Tag and push — the workflow builds + publishes the release automatically
git tag v2.1.1
git push origin v2.1.1
```

The tag name should match the version in `desktop/package.json` (`v` prefix).
The workflow also runs the protocol unit test (`npm test`) before building, so
a release can't be cut with a broken server core.
